Troubleshooting Guide#

과정 전체의 troubleshooting 안내를 한곳에 모았습니다.

모든 명령은 Python environment가 활성화된 하나의 so101-workshop container에서 실행합니다. Get the Code의 terminal을 계속 사용하고 각 실습을 종료한 뒤 다음을 시작하세요. 추가 shell은 선택 사항입니다. Container shell recovery를 참고하세요.

Hardware 문제#

먼저 시도할 방법#

전원 cable을 분리했다가 다시 연결하세요. 다음 명령이 실행되지 않으면 한 번 더 반복합니다. 해결되지 않으면 아래 절차를 진행하세요.

Robot이 응답하지 않음

  1. USB 연결을 확인합니다.

  2. Power LED가 켜졌는지 확인합니다.

  3. 다른 USB port를 시험합니다.

  4. so101-workshop container에서 lerobot-find-port를 실행해 올바른 port인지 확인합니다.

Port를 찾지 못하거나 /dev/ttyACM* 접근 권한 오류

lerobot-find-port가 port를 찾지 못하거나 permission denied가 발생하면:

먼저 USB 연결과 문서에 나온 /dev mount, --privileged 옵션으로 container를 시작했는지 확인합니다. Device를 다시 연결한 뒤 같은 prompt에서 lerobot-find-port를 재실행하세요.

계속 권한 오류가 나고 host 수정이 필요하면:

  1. 현재 실습을 중단하고 main container shell을 종료해 host prompt로 돌아갑니다. 문서의 --rm 실행 방식에서는 container가 종료·제거되지만 mount된 파일은 유지됩니다.

  2. Host에서 확인한 연결 serial port에만 read/write 권한을 부여합니다. 아래 경로는 예시입니다.

sudo chmod 666 /dev/ttyACM0
sudo chmod 666 /dev/ttyACM1

Device 재연결 시 권한이 초기화되므로 필요하면 USB를 다시 연결한 뒤 명령을 반복합니다.

  1. 지속적인 host 접근이 필요하면 사용자를 dialout group(camera는 video)에 추가하고 logout/login합니다.

sudo usermod -a -G dialout "$USER"
sudo usermod -a -G video "$USER"

  1. Get the Code에 따라 container를 재시작하고 port와 저장 설정을 확인합니다.

전원 미연결(All Motors Missing)

모든 motor가 없다는 다음 오류가 보이면:

Missing motor IDs:
  - 1 (expected model: 777)
  - 2 (expected model: 777)
  - 3 (expected model: 777)
  - 4 (expected model: 777)
  - 5 (expected model: 777)
  - 6 (expected model: 777)

Full expected motor list (id: model_number):
{1: 777, 2: 777, 3: 777, 4: 777, 5: 777, 6: 777}

Full found motor list (id: model_number):
{}

Robot의 전원이 연결되지 않았다는 뜻입니다. USB는 통신을 제공하지만 motor에는 별도 전원이 필요합니다.

해결 방법:

  1. Follower robot에 12V 전원을 연결합니다.

  2. Power LED를 확인합니다.

  3. 명령을 재시도합니다.

Motor 하나의 연결 끊김

Motor 하나가 없다는 오류가 보이면:

Full expected motor list (id: model_number):
{1: 777, 2: 777, 3: 777, 4: 777, 5: 777, 6: 777}

Full found motor list (id: model_number):
{2: 777, 3: 777, 4: 777, 5: 777, 6: 777}

Motor 1이 연결되지 않았거나 통신하지 않는 상태입니다. 갑자기 발생했다면 전원을 다시 켜는 것만으로 해결될 수 있습니다.

해결 방법:

  1. Power cycle: 전원 cable을 분리 후 재연결합니다.

  2. 해결되지 않으면 motor cable이 느슨한지 확인합니다.

  3. 누락된 motor의 cable을 확인합니다.

  4. Motor는 daisy chain으로 연결되어 한 곳의 느슨한 연결이 뒤쪽 motor에도 영향을 줄 수 있습니다.

Motor 연결 오류

다음 오류가 보이면:

ConnectionError: Failed to write 'Torque_Enable' on id_=2 with '1' after 1 tries. [TxRxResult] There is no status packet!

특정 motor와 통신에 실패한 상태입니다.

해결 방법:

  1. 전원 확인: Follower의 12V 전원이 연결되고 LED가 켜졌는지 확인합니다.

  2. USB 확인: Cable 양쪽이 단단히 연결되었는지 확인합니다.

  3. Motor 재시작: 전원을 분리했다가 다시 연결합니다.

  4. Motor ID 확인: 해당 ID motor의 연결이 느슨할 수 있습니다.

Calibration 실패

  1. Robot port가 실제 robot의 robot.id와 대응하는지 확인합니다.

  2. 정확한 calibration pose인지 확인합니다.

  3. Motor가 자유롭게 움직이는지 확인합니다.

  4. 초기 pose에서 joint가 limit에 있지 않은지 확인합니다.

  5. 실제 End Stop까지 이동 — Range sweep에서는 wrist roll을 제외한 각 joint를 cable이나 장애물이 아닌 mechanical end stop까지 움직입니다. Wrist-roll range는 LeRobot이 자동 지정합니다. Link 사이에 끼인 cable이나 cable과의 충돌은 잘못된 min/max를 만들 수 있으므로 실제 limit까지 도달하도록 배선을 확인하세요.

  1. 1단계부터 calibration을 다시 실행합니다.

Camera 문제#

Image가 어둡거나 없음

Camera feed가 매우 어둡거나 검다면:

  1. Lens cap 확인 — Cap을 제거했는지 확인하세요. 어둡거나 없는 feed의 흔한 원인입니다.

  2. Camera 전원과 연결을 확인합니다.

  3. so101-workshop에서 lerobot-find-cameras opencv를 실행해 인식을 확인합니다.

Camera Index 변경

Camera를 분리하거나 다시 연결하면 index가 바뀔 수 있습니다.

해결 방법:

  1. so101-workshop에서 lerobot-find-cameras opencv로 현재 index를 확인합니다.

  2. 새 index로 configuration을 갱신합니다.

  3. Capture test image로 검증합니다.

Image가 흐리거나 Focus가 맞지 않음

Feed가 흐리거나 policy가 세부 시각 정보를 처리하기 어려워하면:

  1. Focus 확인 — Camera lens의 초점을 맞춥니다.

  2. 얼룩이나 먼지가 있으면 lens를 닦습니다.

  3. Camera가 고정되어 진동하지 않는지 확인합니다.

잘못된 Camera Feed

Policy가 잘못된 시각 입력을 받으면:

  1. Camera 할당이 예상과 같은지 확인합니다.

  2. Wrist와 external camera가 올바르게 구분되었는지 확인합니다.

  3. lerobot-find-cameras opencv를 다시 실행해 index를 확인합니다.

Policy 배포 문제#

CUDA Out of Memory#

Workshop 평가에서 가장 흔한 원인은 종료하지 않은 추가 policy server의 GPU memory 점유입니다. Ctrl+C로 평가를 끝내고 workshop container 안에서 다음 명령으로 해당 LeRobot policy server를 모두 종료합니다.

pkill -f '[l]erobot\.async_inference\.policy_server'

Server 종료 후 nvidia-smi로 memory를 확인합니다. 시작 및 readiness 명령으로 server 하나만 시작하세요. Policy 평가를 마치고 다음 것을 시작하기 전에 항상 server를 종료합니다.

Inference가 느림#

실제 inference가 느리면 simulation policy server를 종료했는지 확인하세요. 여전히 GPU를 사용할 수 있습니다. Server를 시작한 terminal에서 실행합니다.

kill "$POLICY_SERVER_PID"
wait "$POLICY_SERVER_PID" || true
unset POLICY_SERVER_PID

또는 container의 모든 policy server를 종료합니다.

pkill -f '[l]erobot\.async_inference\.policy_server'

다른 terminal에서 시작한 server라면 그곳에서 종료하세요.

Simulation과 실제 Camera Image 비교#

편집하지 않은 640 × 480 frame 두 개로 simulation dataset에서 실제 workstation으로 옮길 때 policy가 겪는 시각적 차이를 보여줍니다.

Sim/Real Camera 비교 예시와 한계 보기

실제 image는 gripper와 rack highlight가 밝아 세부가 덜 보입니다. Mat는 dark gray보다 blue-gray에 가깝고, 실제 vial에는 simulation의 매끈한 vial과 달리 질감과 주름이 있습니다. Transfer 실패를 조사할 때 lighting, exposure, color response, material을 확인할 이유가 됩니다.

참고

두 frame의 arm pose, gripper opening, vial 배치는 다릅니다. Perception gap을 보여주는 예시이며 camera calibration 시험이 아닙니다. FoV 오류, sensor dynamic range, policy 실패 원인을 입증하지 않습니다.

통제된 비교에는 실제로 측정한 joint pose를 simulation에 재현하고 vial/rack 배치를 맞추며 실제 exposure와 white balance를 기록합니다. Simulation을 바꾸기 전에 결과 image를 비교하세요. Camera response 조정은 수집과 평가 image에 모두 적용한 뒤 실제 성능에 미치는 영향을 시험합니다.

저장 Wrist Image를 겹쳐 정렬 확인#

What Is Sim-to-Real?의 interactive 비교로 image를 겹치고 simulation opacity를 조절하거나 나란히 비교할 수 있습니다. 아래는 다른 image pair입니다.

다른 Pair: Robot 수평 확인#

Image Pair와 Capture 조건 보기

2026년 9월 28일 capture한 두 번째 pair에서는 operator가 실제 base의 수평을 확인하고 rack을 눈으로 맞췄습니다. Simulation은 이 비교에서 capture한 encoder pose, elbow asset correction, 측정 lens intrinsics와 distortion을 사용합니다. 원래 camera mount를 유지하고 후보 offset은 적용하지 않았습니다. Rack은 physics로 안정된 뒤 capture했지만 loose vial은 조금씩 움직여 정렬 기준으로 사용할 수 없습니다.

다른 이미지 쌍: 로봇의 수평 확인 완료

왼쪽은 real 이미지, 오른쪽은 simulation입니다. 두 이미지 모두 640 × 480입니다.

이 예시는 vial-to-rack task에서 simulation과 실제 환경 사이의 perceptual difference를 보여 줍니다. 어떤 차이가 보이나요?

Rack corner, hole, gripper 윤곽은 훨씬 잘 맞지만 밝기, highlight, 표면 detail은 여전히 다릅니다. 실제 scene에는 simulation에 없는 calibration target도 있습니다. Rack 위치를 독립적으로 측정하지 않았고 lens parameter와 scene 정렬이 첫 pair와 달라 정성적 예시일 뿐입니다. Base 수평 효과만을 분리하거나 camera mount calibration을 입증하지 않습니다.

Arm이 Vial 없는 곳으로 향함#

Observation, prediction, motion이 처음 어긋나는 지점을 찾으세요.

  1. 실패한 Pickup 하나를 재검토하세요. Camera image, 실제 GR00T 입력 image, 예측 action, 실행 motion을 비교합니다. Model 입력에 vial이 보이나요?

  2. Simulation에서 Vial만 옮기세요. Arm과 camera는 고정합니다. 예측된 reach가 vial을 따라가나요?

    • Vial을 옮겨도 같은 reach라면 visual conditioning이나 학습된 position bias를 조사합니다.

    • 따라가지만 일정하게 빗나가면 calibration과 action conversion을 확인합니다.

  3. Action Pipeline을 확인하세요. Joint 순서, 단위, normalization, relative-action decoding을 확인하고 상대 action을 두 번 변환하지 않는지 검증합니다.

  4. 더 자주 Replan해 보세요. Model과 scene을 유지하고 16, 8, 4개 action 실행 후 새 prediction을 요청하는 경우를 비교합니다.

  5. 실패 구간의 Data를 보완하세요. Vial 위치, 시작 pose, recovery 접근을 다양하게 한 성공 demonstration을 추가하고 학습에 없는 배치로 시험합니다.

한 번에 한 요인만 바꾸세요. 같은 scene을 반복하고 잘못된 위치로 향한 reach와 성공 pickup을 모두 기록합니다. 통제된 시험 전에는 각 설명을 가설로 다룹니다.

Fixed 또는 “Dummy” Observation으로 Policy 입력 시험#

실제 robot에 prediction을 보내지 않고 offline으로 진단합니다. 두 camera image, 측정 joint state, task instruction이 있는 유효한 저장 observation을 사용하세요. 저장 preprocessing/postprocessing을 유지해 feature 이름, image 변환, normalization, relative-action decoding을 배포와 맞춥니다.

Offline Fixed-Observation 진단 절차 보기

  1. Raw camera frame, 대응 joint state, 실제 preprocessed model input을 저장합니다. Camera 할당, frame 최신성, color 순서, resize, crop을 확인하세요. Live viewer만으로 실제 model 입력을 알 수는 없습니다.

  2. 고정 observation으로 반복 예측하되 trial 사이의 queued action chunk를 reset합니다. 비교 전에 seed를 고정하거나 충분히 반복해 prediction 변동을 측정하세요.

  3. 입력 하나씩 바꿉니다. 의미 있는 시각 시험은 같은 arm/camera pose에서 vial 위치만 다른 두 scene을 렌더링하는 것입니다. Joint state와 task text를 고정하고 decoded action chunk를 비교합니다.

  4. 추가 진단으로 camera 하나를 같은 shape/type의 constant image로 바꾸고 나머지 입력은 유지합니다. 비현실적인 “dummy” 입력은 camera 민감도를 드러낼 수 있지만 비슷한 prediction만으로 vision을 무시한다고 단정할 수는 없습니다. 다른 camera, joint state, 학습된 action prior가 지배적일 수 있습니다.

먼저 offline prediction을 비교합니다. Simulation rollout에서는 조건 사이 environment와 policy queued action을 모두 reset하세요. Pose와 배치 일치의 중요성은 perception-gap 예시를 확인하세요.

실제 Arm에서 기록 Episode Replay#

Recorded-action replay는 policy prediction을 우회해 저장된 joint command가 유사한 실제 trajectory를 만드는지 확인합니다. Policy의 visual reasoning이나 closed-loop recovery를 시험하지는 않습니다.

  1. Dataset viewer에서 짧은 episode를 검토하고 robot, calibration, joint 순서·단위, action 규약, recording FPS를 확인합니다. Workshop action은 처음 5개 joint가 native degree, gripper가 percent입니다. 기록된 absolute action을 직접 사용하고 policy의 relative-action decoding을 적용하지 마세요.

  2. Episode 시작 joint state와 실제 측정을 비교하고 감독하에 위치를 맞춥니다. Replay가 collision-aware한 시작점 이동을 제공하지는 않습니다. 첫 motion 검사에서는 loose object를 치우고 정지 control 곁에 있으세요.

  3. Container에서 dataset과 calibration된 follower ID로 설치된 LeRobot replay 명령을 실행합니다.

lerobot-replay --robot.type=so101_follower --robot.port=/dev/ttyACM0 --robot.id=<follower_id> --robot.use_degrees=true --dataset.repo_id=<hf_user/dataset_name> --dataset.root=./datasets/<hf_user/dataset_name> --dataset.episode=0 --play_sounds=false

  1. Trajectory가 벗어나면 Ctrl+C로 중단하세요. 정량 비교에는 별도 logging으로 실제 joint state와 camera view를 기록해야 하며 replay 명령 자체는 비교 observation을 저장하지 않습니다. 명령뿐 아니라 episode의 observed joint states와 비교하세요. Lag와 contact 때문에 명령과 측정은 다를 수 있습니다.

  2. Recorded command는 같은 motion을 재현하지만 policy rollout은 못 한다면 입력, prediction, action-chunk 실행을 조사합니다. Replay도 다르면 재학습 전에 calibration, joint/gripper mapping, actuator response, mounting, contact를 확인하세요.

Simulation episode도 수집 당시 asset geometry와 joint offset에 의존합니다. 숫자상 joint value가 같다고 실제 pose까지 같다고 볼 수 없습니다. 정적인 camera 비교에서는 실제 arm을 움직이지 않고 encoder를 읽어 simulation에 pose를 재현하세요.

한 번은 되었지만 일관되지 않음

가능한 원인: Distribution shift

해결 방법:

  • Trial 사이 초기 조건이 달라지는지 확인

  • Camera가 안정적으로 고정되고 위치가 바뀌지 않았는지 확인

Grasp가 항상 같은 양만큼 빗나감

가능한 원인: Calibration 또는 camera 위치

해결 방법:

  • Robot calibration 재실행

  • Camera 위치 확인

  • Workspace가 학습 조건과 맞는지 확인

Simulation과 Display 문제#

Simulation Camera Image가 없음

--cameras all presets=newton,ovrtx_renderer를 명시하세요. --cameras none은 의도적으로 image를 끕니다. ovrtx 첫 실행은 cache 준비에 몇 분이 걸릴 수 있습니다.

Browser가 비거나 Control이 동작하지 않음

--browser-display로 실행하고 host에서 http://localhost:8090을 엽니다. Keyboard control을 위해 browser에 focus를 두세요. Recording mode의 Space는 시작/저장, C는 폐기, R은 폐기/reset입니다. Viewer에는 tab 하나만 연결합니다.

문서의 host networking을 사용하세요. Display port는 8090, 49100, 47998이며 같은 port의 다른 session을 종료합니다. --browser-display와 --rerun은 함께 사용할 수 없고 Rerun/headless에는 recording keyboard control이 없습니다.

Policy Server 또는 Checkpoint 오류

같은 container terminal에서 Sim Evaluation의 background server 시작과 readiness 검사를 따릅니다. Client는 --server_address localhost:8080을 사용합니다.

Timeout이나 연결 실패 시 tail -n 40 outputs/policy-server.log를 확인하고 오류를 해결한 뒤 재시도하세요. 같은 port에 중복 server를 띄우지 마세요. 평가 후 server cleanup을 수행합니다.

MODEL_ID가 configuration과 processor를 포함한 LeRobot GR00T 1.7 policy인지, server가 해당 local 경로나 Hub repo에 접근 가능한지 확인합니다. Rename map은 feature 이름만 처리합니다. Checkpoint Compatibility를 참고하세요.

Dataset과 Recording 문제#

자동 수집 Dataset이 아직 Export되지 않음

vials_state_machine --record는 성공 episode를 임시 저장하고 --num_episodes에 도달하면 LeRobot dataset을 조립합니다. 목표는 시도 횟수가 아닌 성공 episode 수입니다. Terminal 수집 수를 보고 최종 export를 기다린 뒤 lerobot-dataset-viz나 upload를 실행하세요. 조기 중단 시 완성되지 않은 임시 episode만 남을 수 있습니다.

--cameras all presets=newton,ovrtx_renderer로 두 camera를 켜고 --repo_id, --task_name을 지정합니다. Automated Data Collection을 확인하세요.

Local Recording Dataset을 학습에서 찾지 못함

실습의 lerobot-train은 Hub ID로 dataset을 선택합니다. 학습 전에 ./datasets/<repo_id>를 검토하고 같은 dataset repo에 upload하세요. 새 shell에서는 HF_USER, DATASET_NAME, 파생 training variable을 다시 설정해야 합니다. 일반 export는 shell 간 유지되지 않습니다.

Dataset이 이미 존재함

Simulation recording 경로는 datasets/<repo_id>입니다. --resume으로 추가하거나 다른 --repo_id로 새 수집을 시작하세요. 실제 recording은 --dataset.repo_id, --dataset.root를 사용합니다. 경로 변경 전에 기존 episode를 확인하고 보존합니다.

Dataset의 Image 또는 마지막 Episode가 없음

두 camera와 renderer preset으로 기록합니다. Saving 표시가 사라지고 terminal에 각 episode 저장 완료가 나올 때까지 기다리세요. Container 종료 전에 Ctrl+C shutdown을 끝까지 기다립니다.

같은 repo ID와 --root ./datasets/<repo_id>로 lerobot-dataset-viz를 실행해 저장 data를 확인합니다.

  1. 이 안내에서 해당 error message를 찾아보세요.

  3. 시각 입력이 이상하면 camera 탐지를 다시 실행하세요.

  4. 문제가 남으면 위 진단 절차를 반복하세요.
